## Problem (verified)

- **Today we are only a client.** `frontend/lib/features/code/harness/everyai/mcp_io.dart` (386 lines):
  `McpConnection.open` (l.24) does `initialize` with `protocolVersion: '2025-06-18'` (l.45), then
  `notifications/initialized`, then paged `tools/list`. `_HttpMcp` (l.224) POSTs with
  `Accept: application/json, text/event-stream`, `MCP-Protocol-Version: 2025-06-18`, echoes `Mcp-Session-Id` if the
  server sets one, reads either JSON or SSE `data:` lines (other lines are skipped, so SSE comments are fine) until
  the reply with its id, and sends `DELETE` on close **only when a session id was given** (l.300). `call()` uses a
  5 min client timeout (l.68); its `cancel` parameter is unused. The only caller is `McpTools.start` in
  `everyai_harness_io.dart:147`. There is no unit test of `McpConnection` over HTTP (the one MCP test,
  `everyai_harness_test.dart:630`, starts a stdio Python fake). There is no HTTP server anywhere in `lib/`
  (tests bind `HttpServer` on loopback: `everyai_harness_test.dart:46` FakeGateway, `compaction_test.dart:181`).
- **Tool schemas that exist** (all OpenAI-style, `parameters`, not MCP `inputSchema`):
  - `askUserQuestionSpec`, `presentPlanSpec` (`domain/agent_mode.dart:174`, `:307`), flat `{name, description,
    parameters, annotations}`. Their descriptions end with "stop and end your turn"; `clientToolSpecs(held: true)`
    (`agent_mode.dart:257`) swaps in the held wording ("The call waits while the user answers in the app; their
    answers come back as the result of this call"). The held wording is the right one for MCP: the answer is the
    call's result.
  - `memoryToolSpec` (`harness/everyai/project_notes_io.dart:89`), `final`, wrapped `{type: function, function:
    {...}}`; runner `runMemory(root, args)` (l.119) returns `ToolOutput`. Its description promises "every later
    session in this project starts with" the memory: true for the EveryAI harness (`projectNotesBlock`), and only
    true for an external lead if the briefing (s1/e2) puts `projectNotesBlock(root)` into the session skill.
  - `bugCheckSpec` (`domain/phases.dart:41`), flat, no annotations. Runs only inside `_bugCheck`
    (`everyai_harness_io.dart:1590`), which needs a `PhaseFlow` and the session's bash tool; it is listed only for
    `bugfix` flows (l.592).
  - **Saved plans have no tool.** Only `savePlan`/`latestPlan`/`plansDir` (`project_notes_io.dart:20-45`); plans are
    saved when `present_plan` is approved (`everyai_harness_io.dart:335`). A new small spec is needed.
- **Spec claim that is wrong:** "AppLifecycleListener pattern used elsewhere". It was used only by the OpenHands
  `sidecarProvider` (added in 3c99b6b) and was deleted with it in fc0cc69; `grep AppLifecycle lib/` is empty now.
  Nothing needs it here: a loopback listening socket dies with the process. A Riverpod `ref.onDispose(stop)` (the
  pattern in `core/providers.dart:27`, `panes_providers.dart:93`) is enough.
- **Spec claim that is out of date:** "initialize, notifications/initialized, ping; protocol version negotiation per
  the current MCP spec". The current spec is **2026-07-28**, which removes `initialize`, `notifications/initialized`,
  `ping` and `Mcp-Session-Id`, and adds `server/discover`, per-request `_meta` versions and `Mcp-Method`/`Mcp-Name`
  headers ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), SEP-2575/2567). The
  CLIs we will drive are mostly on the legacy (handshake) era: our own client sends 2025-06-18; Claude Code 2.1.318's
  binary carries version strings for 2024-11-05 … 2026-07-28 (checked with `strings`), so it may probe modern first.
  So the server must be **dual-era** (the spec's term), which the spec allows on one endpoint
  ([versioning, backward compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)).
- **Backend timeout semantics to mirror** (`backend-exp/src/chat.zig:887 waitForApp`, `config.zig:68`
  `client_tool_timeout_ms = 300_000`): SSE comments every 15 s while waiting; on timeout the model gets
  `Error (timeout): the app did not answer this <name> call within 300 s. Carry on without its result.` and the UI
  gets `tool_status failed, detail "timed out"`.
- **Contract** (`~/.claude/plans/multi-harness.md`, Shared contract): `SessionSpec.briefing` =
  `DriverBriefing {mcpUrl, mcpToken, skillDir, sessionSkill}`, set by the controller (run 2, lane e2). So this lane
  exposes exactly `(url, token)` per session plus revoke; d1 owns `drivers/` and `code_providers.dart`.

## Prior art (cited)

- **MCP spec, Streamable HTTP.** 2025-11-25:
  <https://modelcontextprotocol.io/specification/2025-11-25/basic/transports> (POST per message; notifications → 202;
  requests → JSON or SSE; GET may be 405; sessions optional ("MAY assign"); `MCP-Protocol-Version` header, unsupported
  → 400, absent → assume 2025-03-26; "Disconnection SHOULD NOT be interpreted as the client cancelling", cancel with
  `notifications/cancelled`). 2026-07-28:
  <https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http> ("Closing the SSE
  response stream MUST be treated by the server as cancellation"; required `MCP-Protocol-Version`, `Mcp-Method`,
  `Mcp-Name` headers, mismatch → 400 `-32020 HeaderMismatch`; unknown method → 404 `-32601`; to older clients: GET/
  DELETE → 405, ignore `Mcp-Session-Id`, never mint one). Both: "Servers MUST validate the Origin header … If the
  Origin header is present and invalid, servers MUST respond with HTTP 403", "SHOULD bind only to localhost". Discover:
  <https://modelcontextprotocol.io/specification/2026-07-28/server/discover> (`{resultType, supportedVersions,
  capabilities, _meta.io.modelcontextprotocol/serverInfo, instructions?, ttlMs, cacheScope}`), unsupported version →
  `-32022` with `data {supported, requested}`. Results carry `resultType: "complete"`; list results `ttlMs` +
  `cacheScope`; `tools/list` in deterministic order (changelog minor 3, good for prompt caches).
- **Official TS SDK** (MIT): DNS-rebinding guards `hostHeaderValidation(allowed)` / `localhostHostValidation()`
  (accepts `localhost`, `127.0.0.1`, `[::1]`, ignoring the port; 403 with a JSON-RPC error), turned on by default
  when bound to loopback: <https://ts.sdk.modelcontextprotocol.io/v2/api/@modelcontextprotocol/node/middleware/hostHeaderValidation.html>.
  Its `StreamableHTTPServerTransport` stateless mode (`sessionIdGenerator: undefined`) is the shape we want. We copy
  no code; the idea (Host allowlist + Origin check) is ~15 lines.
- **Why both a token and the Host/Origin check:** CVE-2025-52882, the Claude Code IDE extensions' localhost
  WebSocket server took connections from any origin; the fix checks the lock-file auth token
  (<https://securitylabs.datadoghq.com/articles/claude-mcp-cve-2025-52882/>). The MCP Inspector's localhost proxy had
  the same class of bug (CVE-2025-49596, no auth on a local port; from memory, not re-checked).
- **T3 Code** (`docs/research/t3code.md` §"Does it inject its own harness?"): an MCP server `t3-code` per provider
  session at `http://127.0.0.1:<port>/mcp`, bearer token scoped to thread + provider session, idle expiry, revoked on
  release, injected via Codex `-c mcp_servers…`, Claude `mcpServers`, ACP `session/new.mcpServers`. Same design.
- **dart_mcp** (labs.dart.dev, BSD-3, 0.5.2): <https://pub.dev/packages/dart_mcp>. Streamable HTTP is listed as
  "Unsupported at this time", no cancellation, no 2026-07-28, "experimental". Not usable for the server transport;
  wrapping its `MCPServer` over a hand-written HTTP channel would cost more than the JSON-RPC itself. **Write it
  ourselves.**
- **Client timeouts we will meet** (matter for the held 300 s calls; the briefing lane sets them):
  Codex `mcp_servers.<n>.tool_timeout_sec` default 60 s (<https://www.tembo.io/blog/codex-cli-mcp>,
  <https://github.com/openai/codex/issues/15779>; one blog claims a later default of 300, unverified). Claude Code
  `MCP_TOOL_TIMEOUT` (documented default 100000000 ms) and, since 2.1.187, a 5 min idle abort for remote MCP calls,
  `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` (<https://claudeissues.com/issue/70441-docs-mcp-docs-omit-remote-tool-idle-timeout-and-claude-code-mcp-tool-idle-timeou>;
  default unconfirmed). Our own `McpConnection.call` times out at exactly 5 min.
- **dart:io disconnect detection, probed** (scratch script, not committed): an idle `HttpResponse` with SSE headers
  never reported a client close (`response.done` did not complete within 6 s, even with periodic writes + flush).
  After `response.detachSocket()` (with `chunkedTransferEncoding = false`, `persistentConnection = false`), the
  socket's `onDone` fired **1 ms** after the client cancelled, and `HttpClient`/`package:http` parsed the
  close-delimited SSE body fine. So held calls answer over a detached socket.

## Design

Files (all new, under `frontend/lib/features/code/host/`):

1. `host.dart` (pure Dart, ~90 lines): the shared types and the tool list, plus the conditional import
   (`import 'host_server_stub.dart' if (dart.library.io) 'host_server_io.dart' as impl;`, the `pty.dart` pattern).
   - `final class HostCall {String id; String sessionId; String name; Map<String, Object?> args; Future<HostEnd>
     ended;}`; `enum HostEnd {timedOut, sessionClosed, clientGone, cancelled}` (`ended` completes only when the call
     is abandoned; the implementation withdraws its card then).
   - `typedef HostResult = ({String text, bool isError});` (own type: `ToolOutput` lives in `tools_io.dart`, an io
     file the stub can't import).
   - `abstract interface class HostTools { Future<HostResult> call(HostCall call); }`. One generic method: the run-2
     controller already dispatches client tools by name (question/plan cards from an `ActionCall`), and memory /
     saved plans are one-liners over `runMemory`/`latestPlan`. Typed per-tool methods would duplicate that switch.
   - `hostToolSpecs` (a top-level `final`, built once, fixed order, MCP shape `{name, description, inputSchema,
     annotations?}`), converted from the existing constants by a small `_mcpTool(spec)` that accepts both the flat and
     the `{function: …}` shape: `ask_user_question` and `present_plan` taken from `clientToolSpecs(held: true)` by
     name (no edit to `agent_mode.dart`), `memoryToolSpec`, `bugCheckSpec`, and one new `savedPlansSpec`
     (`saved_plans {name?}`: without a name, the saved plans newest first with their titles; with one, its text).
     Every session token sees all five; `bug_check` outside Bug fix mode answers with the existing error text
     ("bug_check is for Bug fix mode."), as the harness does, so the list stays fixed per server (cache-stable for
     the external CLI). `heldHostTools = {askUserQuestionTool, presentPlanTool}` get the wait limit.
   - `HostToken = ({Uri url, String token})`, matching `DriverBriefing.mcpUrl/mcpToken`.
   - `abstract interface class HostServer { Future<HostToken> mint(String sessionId, HostTools tools); void
     touch(String token); Future<void> revoke(String token); Future<void> revokeSession(String sessionId); Future<void>
     stop(); }` and `HostServer createHostServer({...})` from `impl`.
2. `host_server_io.dart` (~300 lines): the server.
   - **Lifecycle.** Bound lazily on the first `mint`: `HttpServer.bind(InternetAddress.loopbackIPv4, 0)`; URL
     `http://127.0.0.1:<port>/mcp`. When the last token goes (revoke/expiry noticed), the server closes; the next mint
     binds again (new port; no live token can hold the old URL). Bind/close serialised on one `Future` chain. No
     lifecycle listener (see Problem).
   - **Tokens.** `Random.secure()` 32 bytes, base64url (256 bit), prefix `eai_host_`. In memory only, `{token,
     sessionId, tools, lastUsed}`. Lookup scans the live tokens and compares each with a constant-time byte compare
     (xor-accumulate, no early exit); n is a handful. Idle expiry (default 12 h, injected `now()` for tests) is
     checked lazily on each request and on mint; any request, `touch()` (the controller calls it at each turn) and a
     pending call keep a token alive. `revokeSession` ends every pending call of the session (`sessionClosed`; the
     client gets the tool result `Error: the EveryAI session ended.`), then drops its tokens. Grant kinds: only
     `session` is built; Stage 5's `outside` grant (scopes such as list/start/message sessions, minted from Settings)
     is a second variant of the same record with its own tool list. Not built now (nothing would use it).
   - **Request checks, in order** (each on every request):
     1. Path must be `/mcp`, else 404.
     2. Host header must be `127.0.0.1:<port>` or `localhost:<port>` (or `[::1]:<port>`): else 403. An `Origin`
        header, if present, must be `http://127.0.0.1:<port>` / `http://localhost:<port>`: else 403 (body: JSON-RPC
        error, no id). This is the DNS-rebinding defence; CLIs send no Origin.
     3. `Authorization: Bearer <token>` must name a live token: else 401 with `WWW-Authenticate: Bearer
        error="invalid_token"` (missing, unknown, expired and revoked look the same).
     4. GET and DELETE → 405 (no server stream, no sessions). Body > 4 MiB → 413. Body not one JSON object (batches
        were dropped in 2025-06-18) → 400.
   - **Era per request.** If `params._meta['io.modelcontextprotocol/protocolVersion']` is present → modern: version
     must be `2026-07-28` (else 400, `-32022 {supported, requested}`), `MCP-Protocol-Version`, `Mcp-Method` and, for
     `tools/call`, `Mcp-Name` (decoding the `=?base64?…?=` form) must match the body (else 400, `-32020`); results get
     `resultType: "complete"`; list/discover results get `ttlMs` + `cacheScope: "private"`. Otherwise legacy: the
     `MCP-Protocol-Version` header, if present, must be one of `2025-11-25, 2025-06-18, 2025-03-26` (else 400).
     Supported list: `['2026-07-28', '2025-11-25', '2025-06-18', '2025-03-26']`.
   - **Methods.**
     - `initialize`: echo the client's `protocolVersion` if it is a supported legacy one, else answer `2025-11-25`
       (negotiation per 2025-11-25 lifecycle); `{protocolVersion, capabilities: {tools: {listChanged: false}},
       serverInfo: {name: 'EveryAI', version}}`. No `Mcp-Session-Id` (stateless; allowed in both eras).
     - `server/discover`: `{resultType, supportedVersions, capabilities, _meta.serverInfo, ttlMs, cacheScope}`.
     - `notifications/initialized` and other notifications → 202. `notifications/cancelled {requestId}` → 202 and ends
       the matching pending call of the same token (`cancelled`).
     - `ping` → `{}` (legacy only; harmless in modern).
     - `tools/list` → `{tools: hostToolSpecs}` (single page, no cursor).
     - `tools/call`: unknown name → JSON-RPC `-32602`. Otherwise answered over a **detached socket SSE stream**:
       status 200, `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`,
       `Connection: close`, no chunking; then `detachSocket()`. A comment `:\n\n` every 15 s (injected) keeps proxies
       and idle timers quiet; if the request carried `_meta.progressToken`, the same tick sends
       `notifications/progress` instead (some clients reset their timeout on progress; cheap). The socket's `onDone`
       ends the call with `clientGone`. The final event is `data: {"jsonrpc":"2.0","id":…,"result":{content:[{type:
       text, text}], isError}}`, then the socket closes. Other requests answer as plain JSON.
     - Unknown method → modern: 404 `-32601`; legacy: 200 with `-32601`.
   - **Held calls.** For `heldHostTools`, a timer (injected factory, default `Timer.new`, limit 300 s) races
     `tools.call`. On expiry the call's `ended` completes `timedOut` and the client gets `isError: true`,
     `Error (timeout): the user did not answer this <name> call within 300 s. Carry on without its result.` (the
     backend's wording, "the app" → "the user"). Every end path (timeout, revoke, disconnect, cancel) completes
     `ended` once and makes a late `tools.call` result a no-op. A throw from `tools.call` becomes `isError: true,
     "Error: …"`.
   Disconnect = cancel in both eras: the legacy spec says disconnect SHOULD NOT mean cancel because a client might
   resume the stream; we offer no resumption (GET is 405), so the answer could never arrive and keeping the card open
   would only mislead the user.
3. `host_server_stub.dart` (~20 lines): `createHostServer` returns a server whose `mint` throws
   `UnsupportedError('EveryAI can host tools on desktop only.')` (web/mobile never run external leads).
4. `host_providers.dart` (~10 lines): `final hostServerProvider = Provider<HostServer>((ref) { final s =
   createHostServer(); ref.onDispose(() => unawaited(s.stop())); return s; });`. e2 reads it in run 2; nothing here
   touches `code_providers.dart` or `drivers/`.

Run-2 notes for other lanes (not built here): e2's `HostTools` turns a held call into the same `ActionCall` +
`waiting_for_confirmation` the transcript already renders, completes the future from the card, withdraws the card on
`ended`; memory → `runMemory(worktree, args)`; saved_plans → `plansDir`/`latestPlan`; present_plan approval →
`savePlan`. s1's recipes must set client timeouts above 300 s (Codex `tool_timeout_sec = 330`; Claude
`MCP_TOOL_TIMEOUT` and `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` ≥ 330000) and include `projectNotesBlock` in the session
skill. c1 should disallow Claude's native `AskUserQuestion` so the model uses ours (`mcp__everyai__ask_user_question`).

## Simplicity check

- One generic `HostTools.call` instead of five typed methods; the tool list is constants reused from three files plus
  one new spec. No sessions, no resumability, no GET stream, no batching, no OAuth metadata, no `instructions`
  string (the session skill carries the guidance, so no prompt text is added here and nothing needs a "Prompt
  reason").
- Is dual-era overengineered? The modern branch is ~40 lines (one `_meta` read, three header compares, `resultType`/
  `ttlMs` fields, `server/discover`). Dropping it risks a modern-first client (Claude 2.1.318 knows 2026-07-28)
  getting a non-modern 200/-32601 and deciding wrongly; the spec only guarantees the dual-era server works with every
  client. Keep it, but it is the first thing to cut if review wants less.
- `notifications/progress` on the keep-alive tick is optional (5 lines); keep only if review agrees it may help Claude's
  idle abort. The detached socket is not optional: it is the only way dart:io tells us the client left.
- Outside-agent grants are designed, not coded.

## Risks

- **Client-side timeouts shorter than ours** (Codex 60 s default) turn every question card into a client error
  after a minute unless s1 sets them. Our own `McpConnection.call` times out at exactly 300 s, racing the server's
  300 s: fine for tests (injected short limit), worth a margin if the EveryAI harness ever uses the host.
- **401 makes some clients start OAuth discovery** (`/.well-known/oauth-protected-resource` → our 404); the user may
  see "needs authentication" for a revoked/expired token. Acceptable: those tokens are dead on purpose.
- **Idle expiry vs long-lived CLI processes.** A stream-json Claude process lives across turns; a 12 h idle limit plus
  `touch` per turn avoids silent expiry. If e2 forgets `touch`, tools break after 12 h idle.
- **Detached sockets** bypass `HttpServer`'s response handling: we write SSE framing ourselves and must close the
  socket on every path (timeout, revoke, stop) or leak it. `stop()` must end pending calls first.
- **Modern-era details** (`Mcp-Name` base64 sentinel, `ttlMs` values) are built from the spec text, not from a recorded
  client; no installed CLI is known to speak 2026-07-28 to HTTP servers yet. Mark modern tests "spec-derived".
- **Tool names inside descriptions**: `bug_check`'s text says "through ask_user_question"; Claude sees
  `mcp__everyai__ask_user_question`. Models cope; changing it would change the EveryAI harness's cached prompt.
- **Port reuse**: after a stop and re-bind, a stale CLI may hit a different local service on the old port with our
  token in its header. Tokens are useless elsewhere, but this leaks one to whatever listens there; low risk on
  loopback; keeping the server up while any session is open (the normal case) avoids it.

## Tests

`frontend/test/features/host_server_test.dart` (real loopback sockets, no sleeps, injected clock/timer):
1. End to end with our own client: `McpConnection.open('everyai', {'url': token.url, 'headers': {'Authorization':
   'Bearer …'}})` → `tools` names in the fixed order; `call('memory', …)` with a fake `HostTools` returns its text.
2. Initialize negotiation: `2025-06-18` echoed; unknown `2024-01-01` → `2025-11-25`; no `Mcp-Session-Id` in replies.
3. Notifications → 202; `ping` → `{}`; GET / DELETE → 405; batch array → 400; unknown method → -32601.
4. Auth: missing, wrong, revoked (`revoke`), expired (advance the injected `now` past the idle limit) → 401 with
   `WWW-Authenticate`; `touch` keeps a token alive across the same advance.
5. DNS rebinding: `Origin: http://evil.example` → 403; `Host: evil.example:<port>` → 403; valid Origin passes.
6. Version header: legacy `MCP-Protocol-Version: 1999-01-01` → 400. Modern (spec-derived): `server/discover`;
   `tools/list` with `_meta` 2026-07-28 → `resultType: complete`, `ttlMs`; `Mcp-Method` mismatch → 400 `-32020`;
   `_meta` version `2027-01-01` → 400 `-32022` with `supported`.
7. Held call resolved: fake `HostTools` holds a `Completer`; the test awaits "call arrived" (a completer the fake
   completes), completes it, and the client gets the answer.
8. Held call timed out: injected timer factory records the timer; the test fires it → client result starts with
   `Error (timeout)`, `isError`; `HostCall.ended` == `timedOut`; a late completion is ignored.
9. Session close cancels: pending call, then `revokeSession` → client gets `Error: the EveryAI session ended.`,
   `ended` == `sessionClosed`, the token now 401s.
10. Client disconnect: raw `HttpClient` POST of `tools/call`, read the headers, cancel the subscription /
    `close(force: true)` → await `ended` == `clientGone` (event-driven; the probe showed ~1 ms).
11. `notifications/cancelled {requestId}` ends the pending call (`cancelled`).
12. Lifecycle: after the last `revoke` the port refuses connections; the next `mint` gives a working URL.
Plus `flutter analyze` clean and the full `flutter test` before the last commit; no backend change, so no zig run.

## Review (refix, commit 63919dc)

Fixed:
- **Revoked mid-body still ran the call** (major, confirmed by a test that failed before the fix): the token is
  re-checked after the body is read (401), and `_call` returns without dispatching when the grant went away during
  `detachSocket`. Test: "a token revoked while its call body is read runs nothing" (an injected `now` hook marks the
  moment auth passed).
- **present_plan timeout read as approval** (major, reported twice): `_timeoutText` per tool. present_plan: "The
  plan is NOT approved: do not start building it. End your turn and wait…"; ask_user_question: go on only where a
  choice is clearly safe and say what was assumed, else ask again. Test asserts the plan wording.
- **bug_check runs agent commands outside the CLI sandbox** (major): listed and callable only for `mint(…, bugFix:
  true)` (tool list fixed per grant, still cache-stable per agent), MCP annotations `readOnlyHint: false,
  destructiveHint: true`, and the `HostTools` doc requires the session's permission decision before a `command` runs.
  This also settles the minor "bug_check listed for every session" finding.
- **`_serial` poisoned by one failed bind** (minor): the chain swallows errors, the caller still gets its own; a
  failed mint removes its grant. Test with an injected `bind` (io-only, `@visibleForTesting`).
- **Idle expiry** (minor + nit, and the major "touch can't revive"): an expiry timer for the earliest idle grant
  closes the server when the last one expires with no traffic; `touch` returns `bool` (false = expired: restart the
  agent with a fresh mint). Idle expiry itself stays, because the plan (`multi-harness.md` lane m1) asks for it; run 2
  must call `touch` at each turn and act on false. Tests: expiry timer closes the port; touch after expiry is false.
- **Wrongly typed params/method/arguments** (nit, trivial): pattern matches, 400 -32600 / 200 -32602.

Rejected: none. Not done: dropping idle expiry for session tokens entirely (the review's simplest option), since
the plan names idle expiry as a requirement; worth asking the owner in run 2 if `touch` handling proves awkward.
