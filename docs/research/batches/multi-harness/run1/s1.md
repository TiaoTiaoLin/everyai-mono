## Problem (verified)

- Skills today reach only the EveryAI harness: `code_providers.dart:318-319` calls `codeSkillsFor(ref, projectId)`
  (`skills/skills_providers.dart`), which re-scans disk, applies `sessionSkills(all, settings, projectId)`
  (`skill_catalog.dart`: active = usable + enabled + trusted-now-by-digest, sorted by name, project > library > shared) and maps each
  through `openHandsSkill(s)`. Result goes in `SessionSpec.skills` (`harness/harness.dart:28,112`) as `List<Map<String,Object?>>`. The
  name and doc comments still say OpenHands; that harness is gone (c9b1cb8), so the map is just our own shape now. External CLIs need
  the folders, not these maps.
- The pieces to reuse exist: `InstalledSkill` (`dir`, `files` relative sorted without SKILL.md, `manifest`, `digest`, `source`),
  `SkillManifest` (name, description, body, license, compatibility, allowedTools, metadata), `escapeInlineCommands`, `checkSkill`
  rules (no links, no `..`, depth <= 6, <= 500 files, no compiled binaries), `skillNameProblems`. There is no writer for a full
  SKILL.md (`slash/skills/skill_md.dart` `SkillMd.toSource` emits only name/description/body, drops license/metadata).
- Session data lives in App Support: `EveryAIHarness._dirFor` -> `<dataDir>/everyai-sessions/<id>/` (`everyai_harness_io.dart:51`);
  `git_service_io.dart:21 dataDir()`. Nothing deletes a session dir today (grep: no `delete(recursive` for sessions), so "removed
  with the session" is a new hook the integration must call. `attach`/`statuses` treat the existence of `everyai-sessions/<id>` as
  "this session exists" (`:78`, `:89`), so external drivers should not reuse that exact root without the core lane deciding.
- Workspace facts the session skill must state: worktree = `SessionSpec.workingDir`; project root = main checkout (`projectDir` in
  `code_providers.dart`); `.everyai/` files: `plans/` (`project_notes_io.dart:16`), `memory.md` (`:17`), `spill/` (`domain/spill.dart:9`),
  `uploads/` (`uploads/uploads.dart:6`), `scratch/` (excluded via `excludeScratch`), `commands/`, `agents/`.
- Mode text exists once: `AgentMode.reminder`/`instructions`, `modeNote(mode, text, full:, from:)` and `splitModeNote`
  (`domain/agent_mode.dart:86-175`). The spec asks the session skill to state the "current mode"; a file written once goes stale at
  the first mode switch, and Claude/Codex cache the skill catalog, so that line must not live in the skill (see Design).
- The 4 bundled skills (`assets/skills/*`) all carry `metadata: tool: render_diagram|make_slides|render_svg|create_artifact`, i.e. chat
  UI tools no external CLI has. They are in the library after seeding, so `sessionSkills` returns them. They must be left out of the
  export (Design, filter).
- Inline-command hazard is wider than the existing escape: `escapeInlineCommands` keeps fenced blocks untouched
  (`_commandPattern` group 1) and escapes `` !`cmd` ``. Claude Code additionally runs a fenced block whose info string is `!`
  (docs: "```!" multi-line form) and honours `!` only after whitespace/line start, so the backslash escape also works there
  (code.claude.com/docs/en/skills, "dynamic injection"; "In KEY=!`cmd` it stays literal"). The ```! fence is NOT covered by today's
  escape. Claude also treats `allowed-tools` in skill front matter as pre-approval; passing it through would bypass our floor.
- No existing `drivers/` or `briefing/` folder in the worktree; `SessionSpec` has no `briefing` yet (core lane adds it).

## Design

Folder layout, one per session (caller passes `sessionDir`, e.g. `<dataDir>/driver-sessions/<id>`; see Risks for the name):

```
<sessionDir>/briefing/                 # = the Claude plugin root; deleted by removeBriefing
  .claude-plugin/plugin.json           # {"name":"everyai","description":...} written by exportSkills
  skills/<name>/SKILL.md (+ supporting files)   # = skillDir, handed to every CLI that takes a root
  skills/everyai-session/SKILL.md      # generated
```
One `skills/` folder serves all CLIs (Codex `extraRoots`, OpenCode `skills`, Gemini `--include-directories`, Claude via the plugin), so the export runs once.

Files (all new, in `briefing/`; `*_io.dart` + `_stub` for web, as `skills/data/skill_store*.dart` does; recipes and text builders are pure):

1. `briefing_types.dart`: local plain types (integration maps `DriverBriefing` onto them):
   `typedef BriefingInput = ({Uri mcpUrl, String mcpToken, String skillDir, String sessionSkill})`;
   `typedef Delivery = ({List<String> args, Map<String,String> env, List<RpcCall> initRequests, String? firstPrompt})`
   (`RpcCall = ({String method, Map<String,Object?> params})`; `initRequests` = JSON-RPC the driver sends after `initialize` -- Codex needs it;
   `firstPrompt` = text the ACP/Gemini driver prepends once). No `files` field: no recipe needs a file the exporter does not already write
   (Claude's `plugin.json` is part of the export, OpenCode takes config from env). Constants: `everyaiServerName = 'everyai'`, `tokenEnvVar = 'EVERYAI_MCP_TOKEN'`,
   `sessionSkillName = 'everyai-session'`.
2. `skill_export_io.dart` (+ `skill_export_stub.dart`, facade `skill_export.dart`):
   `Future<ExportResult> exportSkills(String sessionDir, List<InstalledSkill> skills, {required String sessionSkillMd})` and `Future<void> removeBriefing(String sessionDir)`.
   - Input is the caller's FRESH scan filtered with `sessionSkills(...)` (same contract as `codeSkillsFor`); the exporter additionally drops skills with
     `metadata['tool']` (chat UI tools) and any named `everyai-session` (generated one wins) and re-checks `usable`.
   - SKILL.md is regenerated from `SkillManifest`, not copied: front matter name, description, license, compatibility, metadata (double-quoted scalars, only `\`,
     `"` and newline escaped, so `parseFrontMatter` round-trips it); **`allowed-tools` is dropped** (Claude pre-approves from it); body goes through
     `defuseInlineCommands` = `escapeInlineCommands` + turning a fence line ```` ```! ```` / `~~~!` into ```` ``` ! ````.
   - Supporting files: copy `InstalledSkill.files` (already vetted by `checkSkill`), but re-lstat each source: skip anything that is not a plain file, or whose
     resolved path leaves the skill dir; reject `..`/absolute rel paths again. Keep exec bit (verify `File.copy` keeps the mode in a test).
   - Idempotent: build the desired `{relpath: bytes|sourceFile}` map; write a file only when missing or different (tmp file in the same dir + rename); delete files and
     empty dirs under `skills/` not in the map. Second run with the same input writes nothing (test compares mtimes/counted writes through an injected writer hook).
   - Containment: refuse when `sessionDir/briefing` or any component created below it is a symlink (`FileSystemEntity.typeSync(p, followLinks:false)`); resolve and check the
     prefix of `sessionDir` before the first write; only the files named by the map are touched. Never reads or writes `~/.claude`, `~/.codex`, `~/.config/opencode`, `~/.gemini`, `~/.agents` writes, or the project.
   - Returns `({String skillDir, List<String> names})`.
3. `session_skill.dart`: `String sessionSkill(SessionSkillInput)`; pure, deterministic. Input: `worktree`, `projectRoot`, `lead` + `others` as `({String name, String model})`, `hostTools`
   (`({String name, String when})`, supplied by the host lane's `HostTools` at integration, so no tool name is hard-coded here), `skillNames`, optional `runtimeProfiles` (String lines).
   Order, constants first: front matter (`name: everyai-session`, `description: Read first in an EveryAI session: ...`); workspace layout (stable text; paths of this session last in that
   section); modes (table built from `AgentMode.values` using the existing `reminder` strings, plus "the current mode is the latest <everyai-mode> tag on the user message; it overrides this
   file"); tools (from `hostTools`); rules incl. "check per part, not per edit" (run the project's check after a finished part, not after each edit; use the `check` tool when the server lists
   it; do not wait on full suites for small changes); then volatile: roster, runtime profiles ("none recorded yet" placeholder). No timestamps. Do not duplicate `modeNote`: the per-turn
   note comes from `modeNote(...)` called by the controller. Spec deviation: the skill does NOT embed the current mode (goes stale; the per-turn note is authoritative).
4. `recipes.dart`: pure functions `Delivery claudeCode(BriefingInput, {bool strictMcp = false, bool grantSkillAccess = true})`, `codex(...)`, `openCode(...)`, `gemini(...)`, `acp(...)`
   plus `Map<String,Object?> acpMcpServer(BriefingInput)` (the `session/new` entry). Shared helper `authHeader(token)`.

## Simplicity check

- Not overengineered if limited to: one export function, one text builder, five small pure recipe functions. Dropped from the spec: a `files` return field, writing any config
  file for Claude/OpenCode/Codex, relocating CODEX_HOME, per-CLI skill folders (one folder serves all), `--settings`, mode in the skill.
- Biggest simplification: the plugin root IS the briefing folder, so the same `skills/` dir feeds four CLIs. The alternative (`--add-dir` with a `.claude/skills` inside) works too but
  needs a second layout and grants write access to the dir; the plugin route is verified loadable and namespaced.
- Gemini and generic ACP get no real skill loading. Do not invent one (extensions live in `~/.gemini`); inline text + readable paths is enough for a first version.
- Do not build a TOML/JSON merge or an "inject into user config" path. If a CLI cannot be scoped from args/env, it gets prompt text.
- The existing `escapeInlineCommands` comment mentions the agent-server; leave it (not this lane), only add the fence defuse in briefing.

## Risks

- Claude/Codex/OpenCode may not auto-load the session skill (descriptions only until invoked). Mitigations: the constant `--append-system-prompt` pointer (Claude), `developerInstructions`
  (Codex), `instructions` (OpenCode). Per-turn `modeNote` carries the hard rule regardless.
- `--append-system-prompt` is recorded once (`--system-prompt-snapshot`); a changed pointer text after an app update is ignored on resume -- harmless, keep it constant.
- Token handling: Claude and Codex read it from env, OpenCode via `{env:...}`; any process in the CLI's tree (the agent's own Bash tool) can read it (`env`). That is a real exposure of
  the per-session bearer: m1 must scope the token (session tools only, revoked at close; already in the plan). ACP carries the token in JSON-RPC (not argv).
- Exported scripts: a skill with `scripts/` runs under the external CLI's own permission model, not our floor. Our approvals only see what the driver surfaces. Keep the skill's `hasScripts`
  info; consider excluding script-bearing skills from external export until e2 decides (cheap filter flag `includeScripts: false`, default false).
- OpenCode `mcp` shape (legacy vs `servers`) and Codex `extraRoots` semantics are UNVERIFIED against a live run; `opencode mcp list` was not run because it may start the shared background service.
- Claude `--mcp-config` entry without `type` silently becomes stdio; the unit test pins `"type":"http"`. Credential-looking var names expand empty (`EVERYAI_MCP_TOKEN` is safe).
- A live `claude` run with `--bare`-style flags would skip plugins? (`--bare` skips plugin sync, `--safe-mode` disables plugins): the c1 lane must not pass them. UNVERIFIED for `-p`.
- File access: Claude restricts reads to working dirs, hence `--add-dir skillDir`; Codex macOS sandbox reads broadly; OpenCode may ask for `external_directory`; Gemini needs `--include-directories`. Reading
  skill supporting files may prompt in some CLIs; harmless.
- Session dir naming collides with `everyai-sessions/<id>` semantics (`statuses`/`attach` use dir existence). Use a different root (`driver-sessions`) or confirm ids never collide with core lane.
- A fixed `everyai` plugin name collides if the user also has a plugin of that name; plugin skills are namespaced per plugin so only the manifest name matters. Low.
- Stale roster in the skill when a harness connects/disconnects: regenerate and re-export (idempotent); Claude watches skill dirs, Codex has `skills/changed` watcher; others pick it up next session.

## Review

Fixed:
- Defuse now matches Claude Code's own patterns: every `!`` is escaped (inside fences too), every fence marker followed by `!` gets a space (any position, blockquote, list, 4+ backticks). Tests run Claude's regexes on the defused text. The session text goes through the same defuse, and the claude recipe adds `--settings {"disableSkillShellExecution":true}`.
